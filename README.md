Topic служит для передачи непрерывных потоков данных, например для передачи данных с датчиков или информации о состоянии робота. Определяется как 
.msg файл.


# Основные характеристики Topic

* Асинхронная односторонняя связь (отправитель не должен ждать, пока получатель обработает сообщение)

* Несколько издателей и подписчиков могут использовать одну и ту же тему

в ROS2 есть такие объекты внутри узла как подписчик и публикатор.

Публикатор является объектом, который отправляет сообщения в определенный топик.

Подписчик подписывается на определенный топик и получает из него сообщение.


Service предзназначен для синхронного взаимодействия по принципу запрос - ответ, имеет формат .srv. Клиент отправляет запрос, а сервер ему отвечает.

# Основные характеристики service

* Синхронная связь (отправитель ждет ответа от другого узла, прежде чем продолжить выполнение своего кода)

* Идеально подходит для кратковременных операций, требующих подтверждения или представления результата ответа на запрос


Action предназначен для выполнения длительных задач с обратной связью, нарпимер для перемещения робота в определенное положение или для выполнения роботом слонжого движения. Формат файла .action. Action позволяет клиентам отправлять цели, получать обратную связь за время выполнения, при необходимости отменять действия и получать результат, если он доступен.

# Основные характеристики action


* Асинхронная обратная связь (отправитель не обяхан ждать ответа как с сервисами)

* Подходит для операций, требующих выполнения в течение некоторого периода.



Также я узнал, что все взаимодействия узлов можно посмотреть через графический интерфейс RQT, выполнив команду rqt_graph в терминале.


# Знакомство с программным комплексом gazebo classic

Следующим этапом стало изучение Gazebo Classic. Я разобрался с запуском симулятора, загрузкой миров и принципом описания моделей.

Постепенно познакомился с форматом SDF, основанным на XML. Изучил назначение элементов world, model, link, visual, collision и pose. Отдельно разобрался с координатами X, Y, Z и углами Roll, Pitch, Yaw, которые в SDF задаются в радианах.

Первой моей задачей стало создание виртуального склада, в нем я расположил два ряда стелажей с проходом шириной 3 метра, по 3 стеллажа в каждом ряду. 
Для моделирования использовал готовую геометрию стеллажа в формате STL. Также изучал модель в FreeCAD, чтобы разобраться с её размерами, расположением торцов полок и местами будущего крепления маркеров.
В конструкции стеллажа была особенность, его центр масс находился в начале системы координат,а эта система координат находилась в нижнем углу стеллажа, по это причине мой стелаж не мог нормально стоять на ровной поверхности, поэтому пришлось сделать его статическим, чтобы он мог стоять ровно и неподвижно.

Следующей задачей стало размещение STag HD13 на торцах полок. Они понадобятся для будущей работы камеры и определения положения относительно известных ориентиров.
Сначала я попробовал создать только один маркер и разместить его на стеллаже. Для этого создал отдельную модель stag_hd13_test.
в состав этой модели вошли: 
* model.config — информация о модели и указание на её SDF-файл;
* model.sdf — геометрия маркера: белая подложка и плоскость размером 9 × 9 см;
* stag.material — настройки графического материала для Gazebo;
* hd13.png — изображение тестового маркера.

При создании модели разобрался, как текстура png накладывается на геометрию и как несколько файлов объединяются в одну модель.

Чтобы вручную не добавлять файл в мир, был реализован скрипт place_test_marker.py.

Скрипт читает исходный warehouse_base.world, создаёт XML-блок include со ссылкой на модель HD13 и заданными координатами, а затем сохраняет результат в новый файл warehouse_hd13_test.world. При этом исходный склад остаётся неизменным.

На данный момент получилась вот такая структура проекта


```text
warehouse_project/
├── worlds/
│   ├── warehouse_base.world
│   └── warehouse_hd13_test.world
├── meshes/
│   └── Стеллаж 6.stl
├── models/
│   └── stag_hd13_test/
│       ├── model.config
│       ├── model.sdf
│       └── materials/
│           ├── scripts/
│           │   └── stag.material
│           └── textures/
│               └── hd13.png
└── scripts/
    └── place_test_marker.py
```

запускается таким образом:

Cоздаем тестовый мир с маркером
python3 ~/warehouse_project/scripts/place_test_marker.py 

Затем перехожу в папку с мирами и запускаю gazebo
cd ~/warehouse_project/worlds
gazebo --verbose ./warehouse_hd13_test.world

Следующим шагом будет создание generate_markers.py, который будет считывать координаты стеллажей из SDF и автоматически размещать по шесть маркеров на каждом из стеллажей. После проверки расопложения маркеров назначу им уникальные id и добавлю им соответствующие HD13.


# Генератор маркеров

После реализации скрипта с загрузкой одного маркера в gazeebo я приступил к реализации скрипта по размещению 36 уникальных  STag маркеров.

Я загрузил с гугл диска необходимые HD13 маркеры.
Для того чтобы роботу было понятно, что у него есть разные ID маркеров, необходимо чтобы в gazebo было создано 36 уникальных моделей HD13. За это  и будет отвечать скрипт. Он также, как и тестовый будет создавать material, config и sdf, но для каждого  png  отдельно. Этот же скрипт и будет выполнять генерацию моделей, проверку расположения стеллажей в базовой  версии мира warehouse_base.world и размещать HD13 по позициям. В конечном результате выполнения скрипта мы будем получать папку models_markers, содержащую в себе модели HD13, и новый мир warehouse_hd13_36.world, в котором уже будут загружены  и  размещены HD13.
Одним из недостатков этого скрипта является то, что  он имеет жесткую привязку к координатам стеллажей и их количеству, к примеру, если  их количество будет другим или координаты их расположения будут отличаться, то  могут возникнуть проблемы .

## Знакомство с URDF (Unified Robot Description Format) и Xacro (XML Macros)

URDF - это XML-документ, который содержит конструкцию робота, его геометрию, соединения между деталями, массу и другие физ. параметры.
Он сообщает, какие детали есть у робота, как они соединены и могут двигаться относительно друг друга, какие у них размеры, масса и моменты инерции, где относительно корпуса находятся колеса и датчики.

Xacro - это инструмент для генерации XML-описания робота. Он позволет использовать переменные, вычисления,макросы, условия и подключение других файлов.

в Xacro переменные можно задавать параметрическим путем, например:

<xacro:property name="body_length" value="0.45"/>

<xacro:property name="body_width" value="0.30"/>

<xacro:property name="body_height" value="0.12"/>



За основу робота возьму пример создания R2D2 с официального туториала ROS2 humble и внесу правки под свое задание.

Для оптимизации urdf файла я решил использовать Xacro
Для этого я создал копию своего файла с расширением .xacro
Зачем было изменение в строке robot, туда я добавил пространство имен с адресом, обозначающем пространство имен xacro xmlns:xacro="http://www.ros.org/wiki/xacro" ,
затем выполнил команду ros2 run xacro xacro warehouse_r2d2.urdf.xacro -o warehouse_r2d2.urdf чтобы сгенерировать через xacro новый urdf
